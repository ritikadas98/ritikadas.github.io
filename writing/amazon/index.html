Customer complaints, ranked every week

A discovery pipeline built on Amazon reviews, and the collection problem nobody warns you about.

Role
Product and build, solo
Type
Shipped product
Surface
Pipeline, dashboard, digest
Method
Built on a fixture, run on live data
Problem
A product manager cannot read every review, so they skim. Skimming feels fine, because you never find out what you missed. The complaint that mattered was in there and nobody counted it.
Decision
Thirteen steps, and AI runs at three of them: cleaning messy text, grouping complaints into themes, judging readiness. Every number a PM then sees is computed in code.
Evidence
Every claim in the digest links to the review behind it, and a citation that cannot be resolved is shown as unverified instead of dressed up as a footnote. Three live runs so far, 32 to 47 signals each.
Outcome
A week of reviews becomes a ranked list a PM could act on. And a finding I did not expect: of three ingestion sources, only one reliably returns anything at all.

It only worked while my laptop was on

I built the first version as an n8n workflow. Twenty-nine nodes on a visual canvas, doing the right thing: take customer reviews, clean them, find themes, score them, email a digest.

Then I tried to put it behind a website and hit the thing nobody mentions about visual automation tools. It has to be running somewhere. Either I leave my machine on, or I pay for hosting. I did not want to do either for a portfolio project.

So I moved it. Every node became a TypeScript module, the canvas became an orchestrator, and the whole thing went onto Cloud Run with scale-to-zero. It costs about ₹40 a month and runs on a schedule with nothing left switched on.

I used Claude for the port. Twenty-nine nodes of working logic, translated instead of reinvented. That is exactly the job worth handing to a model. The design was already settled. What was left was moving it.

Thirteen steps, three of them AI

The pipeline runs in sequence. Normalise, clean, detect regressions, synthesise themes, aggregate. Then score with RICE, compare week over week, assess readiness, format, write to the sheet, send the digest.

AI runs at exactly three of those. It cleans messy review text, it groups complaints into themes, and it assesses whether a theme is ready to act on. Everything a product manager then sees as a number, the RICE score and the week-over-week delta and the counts, is computed in code.

That split is deliberate. A model is good at reading a thousand badly written complaints and noticing four hundred are the same problem. It is not good at arithmetic. It does not need to be.

The chat on top follows the same rule. It cites sources as signal IDs, and every citation is checked against the real signals before it renders. An ID that does not resolve gets an amber unverified chip instead of a footnote that looks real. The share that resolves is logged every turn. That is the closest thing here to an accuracy metric.

Now the part I did not expect

I built three ingestion sources. Two of them produce almost nothing.

The App Store returns an empty list to a datacentre. Apple’s review feed answers with HTTP 200 and zero entries when the request comes from a Google IP. It is not a country mismatch, which is what I assumed for a while. It is an address-range block. The same code on my own connection returns fifty reviews. In production it returns none.

Amazon’s own reviews are readable and useless. The source reaches all eight products it watches. The .com pages are wall-to-wall praise, so the relevance filter correctly drops nearly everything. The .in pages return CAPTCHAs. The mechanism works. There is just nothing to collect.

That leaves the Play Store as the only source I can rely on. A live run pulls fifty reviews. Thirty-two survive the substance filter and get analysed.

Every pipeline diagram starts with an arrow labelled data. The arrow is the hard bit.

What it cannot tell me

No product manager has used this. It runs, it emails, the numbers are real, and nobody’s roadmap has moved because of it.

I know the shape is right. Companies build exactly this internally, or buy it. I chose Amazon because I use it constantly and wanted enterprise-scale mess instead of a tidy dataset.

Knowing the shape is right is not knowing this one is useful. That needs a PM with a real backlog. Someone to tell me the ranking was wrong, or the digest came on the wrong day, or they read three lines and stopped.

The numbers here come from two places, and it matters which. The design was proved against a fixture of 140 signals I wrote myself. I made them deliberately specific, so the pipeline could not get away with a theme called “Search issues.” The limits came from the live runs, which are smaller, messier, and only ever from one source.

Both are honest. Only one is real.
